Managed or custom, first decision

Check Composio managed apps first. Managed apps are the default when they are available. Stay managed if default scopes cover your needs and Composio branding fits your product. You can still white-label the Connect Link page without your own OAuth app.

Go custom if you need your own app name on consent screens, custom scopes beyond defaults, dedicated quota instead of shared quota, faster polling than the managed 2-minute minimum, a custom instance such as a private Salesforce subdomain, or enterprise end-to-end branding. Choosing your own app changes ownership, branding, scopes, and quota, not token custody. You can mix approaches by toolkit.

Source: Composio docs, Managed vs custom auth, checked 2026-10-31.

Live research: submit an app outside the library

Enter an app name or website. The research endpoint searches for official developer and OAuth docs, fetches candidate pages, extracts registration, scope, and review claims, and returns a guide with a research log, sources, and confidence. It does not submit an OAuth app to any provider, and it does not claim approval. If no official docs can be verified, the guide says Unknown instead of inventing a timeline.

How it works: search, fetch candidate pages, check for OAuth, client ID, redirect, and scope mentions, extract scope-like tokens, build steps from what was actually fetched, and log every attempt, success, and failure with a timestamp. Generated guides get a shareable link that survives refresh, because the guide data is encoded in the link and also saved in this browser.

Verification report, sampled checks on 2026-10-31

This report compares an initial claim against an independent source check. It is not a claim that every guide is fully verified.

  • GitHub, no approval for standard scopes: Initial claim was that registration is immediate. Source check, GitHub Docs authorizing OAuth apps and scopes pages, confirmed. Result: confirmed, no separate approval stage for basic scopes.
  • Slack, own workspace versus public distribution: Initial claim was that setup is quick. Source check, Slack Developer Docs installing with OAuth, confirmed for own workspace, and showed public distribution as a separate step with review time not published as one fixed number. Result: corrected, guide now separates own workspace install from public distribution.
  • Google, verification timelines: Initial claim was that verification takes a few days. Source check, Google restricted scope verification page, showed brand verification typically 2 to 3 business days if branding changed, sensitive scope verification up to around 10 days in some guidance, and restricted scope verification several weeks plus a security assessment. Result: corrected to ranges, not a single number, and assessment cost left unknown.
  • Meta, App Review timeline: Initial claim was that a timeline could be stated. Source check found only third-party summaries, no official Meta timeline confirmed. Result: downgraded, guide says varies by permission and review round, with no fixed timeline claimed.
  • Airtable, registration and scopes: Initial claim from secondary guides was that registration gives Client ID and Secret, with scopes for records, comments, schema, webhooks, and user email. Source check, Nango and Formbricks guides plus Pipedream scope lists, confirmed consistently, but official Airtable pages are JavaScript rendered and were not fully extracted. Result: guide kept at Medium confidence, approval and distribution marked Unknown.

Full execution records are in each guide detail, under Execution record, with sources checked, tested notes, and not verified lists.

Pick your agent

Same guide JSON for every agent, with no plugin from this library to install. Give the agent guides.json or one guide JSON, and it follows the same steps, timeline, and checklist a human follows.

  • Claude Code: point it at guides.json or paste one guide JSON
  • OpenAI Codex: add the guide JSON to the task context
  • Cursor: keep guides.json in the project and ask Cursor to build against that guide
  • GitHub Copilot: in agent mode, give it the guide JSON from the repo
  • Gemini CLI: load guides.json first, then ask it to walk the setup step by step
  • OpenClaw: give it the guide JSON as the task spec, with human steps left to you
  • OpenCode: add guides.json to the project and ask it to follow that platform guide
  • Cline: paste the guide JSON into the task
  • Grok Build: give it the guide JSON, then ask it to build the authorize flow from that guide

For agents: machine readable guides

Humans read the cards above. Agents can read the same guides as structured JSON, with no login.

  • /guides.json - full index of all guides
  • /guides/<id>.json - one guide, for example /guides/github.json
  • /llms.txt - a plain text index for agents and crawlers

Each guide JSON uses the same schema: id, name, difficulty, setupTime, approvalWait, steps, timeline, checklist, blockers, agentCan, humanMust, sources, tested, notVerified, confidence, and nextStep. The human cards and the JSON come from the same data, so they do not drift apart.

How to read a guide, and what to trust

Setup time is active work. Approval wait time is waiting for a provider. They are reported separately on purpose. A range means the provider does not publish one fixed number, or the time depends on your submission quality. Unknown means we could not confirm it from a source in this check, not that it is zero.

Full guides were checked against official or close to official docs on 2026-10-31, as noted in each guide. Summary guides are not verified and must be expanded by live research and checked against official docs before use. No account sign-in, app creation, or provider approval was completed for these guides, and no secrets are included.
